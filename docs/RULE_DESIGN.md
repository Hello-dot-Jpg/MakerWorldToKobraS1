# Rule-engine design notes

This began as a design artifact and now records the constraints behind the
active conversion rules. Writing remains conditional on target resolution,
embedded-snapshot reconciliation, and structural/hash validation.

## Rule inputs

A rule needs more context than a leaf setting name:

- exact source member and canonical path;
- source scope (project, printer, process, or filament);
- typed raw JSON value;
- schema form (scalar versus array slot);
- target occurrences and cross-file conflicts;
- whether a value such as `0`, `nil`, `auto`, or a percentage is a sentinel;
- optional object/plate/filament-slot context.

Matching only `name` is useful for comparison but unsafe for modification.

## Candidate KEEP areas

- 3D model resources, meshes, components, and build transforms;
- model-settings objects, parts, model instances, plates, and assemblies;
- layer height, walls, top/bottom shells, infill density/pattern;
- supports, support painting/blockers/enforcers, seams and seam painting;
- ironing, brim/raft intent, modifiers, colour painting, and assignments;
- unknown settings outside a verified machine-definition replacement region.

Target geometry and plate layout are never merged into the source.

## Candidate CLAMP keys

The Bambu key-map upstream and both supplied files confirm these names exist:

- `outer_wall_speed`, `inner_wall_speed`, `sparse_infill_speed`;
- `internal_solid_infill_speed`, `top_surface_speed`, `bridge_speed`;
- `gap_infill_speed`, `support_speed`, `support_interface_speed`;
- `travel_speed`;
- `default_acceleration`, `outer_wall_acceleration`;
- `inner_wall_acceleration`, `top_surface_acceleration`;
- `travel_acceleration` and initial-layer acceleration variants.

The numeric operation remains `min(source, verified_target_limit)`. It may run
only after strict decimal parsing and setting-specific sentinel handling. For
example, source `inner_wall_acceleration = "0"` may mean inherit/default; a
literal `min(0, target)` would incorrectly force zero acceleration.

## Candidate REPLACE areas

- verified printer identity and preset identity;
- printable area/height, kinematics, nozzle hardware, and G-code flavour;
- verified machine maximum speeds, accelerations, jerk, and extruder limits;
- machine start/end/layer/tool-change/pause G-code and hardware macros;
- fan, bed, prime/purge, and auxiliary-hardware definitions.

The supplied Kobra candidate has conflicting project and separate machine
profiles. Reviewed Anycubic source establishes the ordering: embedded profiles
are registered first, then the complete project config is applied. A retargeted
scope may remove one foreign embedded snapshot only when all its substantive
keys are flattened; ambiguous and unflattened cases remain blockers.

The reviewed public Anycubic Slicer Next source defines Normal and Stealth
machine-limit modes, but the locally installed 2.0.0.2 profile deliberately
ships three entries for every Kobra S1 nozzle. The third entry's current
semantics are not proven. Conversion rules must therefore treat each
machine-limit array as opaque, versioned target-profile data and REPLACE the
whole verified array. They must not select, reorder, clamp, or warn about an
individual slot merely from its position.

## TRANSLATE/REVIEW areas

- filament slot and AMS-to-ACE Pro assignment;
- maximum volumetric speed, flow ratio, pressure advance;
- retraction/deretraction, wipe, and tool-change retraction;
- nozzle/bed temperatures, cooling and auxiliary fans;
- purge/flush volumes and conditional filament-change G-code.

These require material, nozzle, printer, and slicer context. Community profile
numbers are evidence for review, not universal defaults.

Nozzle diameter, nozzle material, and hotend construction are separate target
inputs. In particular, a hardened-steel selection must not silently inherit a
brass profile's thermal/flow assumptions, and a PTFE-lined hotend must not
silently inherit an all-metal or ceramic hotend's temperature assumptions.
Until exact hardware ratings are recorded, rules may preserve a lower safe
source value or request review, but must not raise temperature or volumetric
flow merely because another hotend/nozzle combination supports it.

Profile inheritance must be resolved before rules are evaluated. For the
known-good community 0.4 mm hardened-steel target, the official Anycubic 0.4 mm
machine definition supplies the base and the seven-key community machine JSON
supplies the overlay. Associated process and filament profiles are separate
overlays. Bundled 0.25/0.6/0.8 community leaves are not generated by diameter
substitution; when selected, their declared 0.4 mm parent is explicitly replaced
with the installed matching-diameter official parent so stock compatibility is
correct. The plan records this derived chain and requires slicer review.

## Proposed external rule shape

The eventual JSON/YAML rule should contain:

```text
id, action, setting_name, allowed_scopes, source_member_pattern,
value_kind, sentinel_policy, target_selector, confidence, rationale
```

Rules should be versioned and evaluated in dry-run mode first. Every evaluation
must record which rule matched, source and target locations, parsed values,
result, confidence, and warnings. No match means UNKNOWN = KEEP.
